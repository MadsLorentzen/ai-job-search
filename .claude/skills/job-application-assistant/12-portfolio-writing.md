# Portfolio writing from existing projects

Read during daily career reviews, portfolio planning, and project milestone reviews.
Turn work the candidate is already doing into useful Medium article suggestions.
Prefer documenting an existing project over prescribing another project solely to
produce content. This is part of career development alongside applications and learning.

## Recover the project backlog

Read the private candidate profile, project links, project notes, previous learning
reports, and `reports/portfolio-writing.md`. Inspect accessible repositories and
user-provided artifacts before describing implementation or results. User-mentioned
projects are valid ideas, but their names alone do not establish what was built.
If sources are unavailable, retain the idea as needing evidence and specify the
smallest missing input. Do not invent repository URLs, outcomes, or technologies.

Keep personal ideas and drafts in the private workspace. Reusable workflow rules
belong here; the candidate's project inventory does not. Preserve project ideas
provided in conversation in the private backlog when that workspace is available.

## Daily recommendation

Review project changes and the backlog once per daily career run. Recommend at most
one actionable writing step, based on a new milestone, a useful lesson, available
evidence, relevance to target AI/DS/DE roles, and remaining writing effort. Existing
side projects can be worthwhile without a matching job posting. Cite inspected
postings when claiming employer demand; otherwise label relevance as a positioning
judgment. Do not imply publishing guarantees interviews or employment.

For each recommendation provide:
- Project and source path/link, with what has actually been verified.
- Working Medium title, intended reader, and one concrete lesson or question.
- Career relevance: which demonstrated skill or engineering decision it makes visible.
- A brief outline: problem, approach, decisions/tradeoffs, observed result, limitations,
  and reproducible takeaway or repository/demo link where available.
- Missing evidence such as a screenshot, measured comparison, tested commands,
  environment versions, or an explanation of the candidate's contribution.
- One next action with an estimated effort, defaulting to a 20-45 minute task.

Suggest an outline or evidence capture before a full draft when implementation facts
are missing. A work-in-progress lesson is valid if labeled honestly. For local setup
tutorials, verify commands and versions against the project and official documentation;
distinguish a local learning environment from a production deployment. Analysis posts
must identify synthetic data and actual validation limits. Describe AI assistance and
personal contribution accurately. Follow `03-writing-style.md` for drafts.

## Persist and avoid repetition

Maintain one private `reports/portfolio-writing.md` backlog with stable project/topic
IDs, source references, evidence checked date, article angle, status, next action,
last suggestion date, and published URL when verified. Use statuses: idea,
needs_evidence, outline, drafting, ready_for_review, published, deferred.
Record user deferrals and any requested revisit date. Deduplicate overlapping angles.
Only resurface a suggestion when evidence or status changes, a requested revisit date
arrives, or the user asks. An unchanged daily review should not trigger a notification.
Mention progress briefly in `reports/session-handoff.md` rather than duplicating the backlog.

Prepare local outlines and drafts within the authorized scope. A recommendation to
write does not authorize publishing on Medium or posting promotional messages.
Mark published only with a verified public URL or an explicit user report, identifying
which evidence supports it. Apply the reviewed-learning rules in
`.claude/commands/learn-project.md` before promoting claims to application materials;
publication alone is not proof of proficiency.
