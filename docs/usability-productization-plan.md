# AI Job Search 易用性与输入简化落地方案

**文档状态：** 产品化方案基线  
**版本：** 1.0.0  
**建立日期：** 2026-09-01  
**适用范围：** 本地求职工作流、国内招聘平台接入和普通用户使用体验

## 1. 背景与问题定义

当前项目的核心能力已经覆盖职位搜索、标准化、去重、排名、人工导入和申请材料工作流，但主要通过命令行和 Markdown 工作流触发。对不熟悉终端、参数和项目目录的用户来说，存在两个直接问题：

1. 使用成本高：需要打开终端、理解 Python/Bun/CLI 命令、识别错误码并手动维护文件。
2. 输入信息杂：候选人配置、搜索条件、职位正文和平台参数分散在多个文件或命令参数中，首次使用容易漏填或重复填写。

这两个问题不是底层搜索能力不足，而是缺少一个面向普通用户的产品入口和渐进式信息采集层。本方案保留现有 CLI、`.claude/` 规范和本地数据文件，新增一层本地可视化控制台与智能输入编排。

## 2. 产品目标与非目标

### 2.1 目标

- 用户无需直接操作终端即可完成首次设置、搜索、导入、排名和查看结果。
- 首次设置的必填项控制在 5 项以内。
- 用户可以用一句话描述求职目标，系统转换为结构化搜索配置。
- 用户上传或粘贴简历后，系统自动提取候选人画像，只要求确认或修正。
- BOSS/51job 职位导入统一为“粘贴链接，必要时粘贴正文”。
- 所有个人资料、简历、职位正文和 Token 默认保留在本机。
- 保持现有 `/scrape -> /rank -> /apply -> /outcome` 工作流语义不变，CLI 仍可独立运行。

### 2.2 非目标

- 本阶段不建设云端多租户 SaaS。
- 不自动读取浏览器 Cookie、密码、短信验证码或 Token。
- 不绕过 CAPTCHA、登录验证、风控或设备指纹。
- 不自动批量投递、自动私聊或代替用户提交申请。
- 不因增加 UI 而重写现有门户适配器和评分规则。

## 3. 目标用户与使用场景

| 用户类型 | 主要障碍 | 首版解决方式 |
|---|---|---|
| 不熟悉终端的求职者 | 不会执行命令、看不懂错误码 | 本地 Web 控制台、一键启动、动作型提示 |
| 有简历但不想重复录入的用户 | 资料分散、反复填写 | PDF/Word/文本解析后确认 |
| 只想快速筛职位的用户 | 配置项太多 | 一句话目标、模板和默认值 |
| 使用 BOSS/51job 的用户 | 页面受限、复制内容繁琐 | 粘贴链接，必要时粘贴正文，自动归档 |
| 重视隐私的用户 | 不愿上传简历和 Token | 本地优先、敏感数据不进日志 |

## 4. 总体产品方案

### 4.1 推荐形态：本地 Web 控制台

用户双击启动器后，系统启动本地服务并自动打开浏览器页面。用户只接触页面按钮和自然语言输入，底层继续调用现有能力：

```text
本地 Web 控制台
        ↓
本地任务编排层
        ↓
现有门户 CLI / tools / canonical workflow
        ↓
seen_jobs.json、职位原文、候选人配置、申请跟踪
```

本地 Web 形态适合当前项目的原因：

- 不需要先建设账号系统、云数据库和远程文件存储。
- 简历、职位正文和授权配置不离开用户电脑。
- 可以复用现有 Python、Bun 和 CLI，降低重构风险。
- 后续可以打包为 Windows 安装包或桌面壳，不改变业务层。

### 4.2 一键启动体验

首版提供以下入口之一，优先支持 Windows：

```text
启动求职助手.exe
```

开发阶段可先提供：

```powershell
启动求职助手.bat
```

启动器负责检查 Python/Bun、启动本地服务、打开浏览器，并把依赖缺失转换为可执行提示。用户不需要知道 `bun run`、`python tools/...` 或文件路径。

## 5. 核心页面与交互

### 5.1 首页：只保留 5 个核心动作

首页只展示：

1. 开始找职位
2. 导入一个职位
3. 查看匹配结果
4. 完善我的资料
5. 平台状态

高级设置、原始 JSON、命令参数和调试信息放入折叠区域，不干扰主流程。

### 5.2 首次设置向导

首次使用只要求以下最小信息：

| 步骤 | 用户输入 | 系统动作 |
|---|---|---|
| 1 | 一句话求职目标 | 提取职位方向、城市、薪资和办公方式 |
| 2 | 上传简历或粘贴经历 | 提取经历、技能、教育和语言 |
| 3 | 确认提取结果 | 只修正错误，不重复录入 |
| 4 | 选择要启用的平台 | 默认启用无需授权的平台 |
| 5 | 开始搜索 | 生成搜索任务并展示进度 |

默认必填字段不超过 5 项；语言、行业偏好、排除条件等信息采用“稍后补充”。

### 5.3 一句话目标解析

用户可以输入：

```text
北京，Python 后端或数据工程，20K 以上，可接受混合办公
```

转换为内部结构：

```json
{
  "roles": ["Python 后端", "数据工程"],
  "cities": ["北京"],
  "salary_min": 20000,
  "salary_unit": "month",
  "work_mode": ["hybrid", "onsite"]
}
```

解析结果必须先展示给用户确认。无法确定的内容写入待确认项，不得猜测成硬约束；原始句子保留，便于重新解析。

### 5.4 简历自动提取

支持 PDF、Word 和纯文本输入，优先提取：

- 姓名和联系方式
- 工作经历与时间范围
- 技术技能和工具
- 项目经验
- 教育背景
- 语言能力
- 行业和岗位关键词

系统展示“识别结果 + 来源片段 + 置信度/待确认标记”。用户确认后才写入候选人配置；低置信度字段不得直接成为排名硬门槛。

### 5.5 渐进式资料补充

资料按使用时机逐步补齐：

- 搜索前：岗位、城市、薪资、办公方式。
- 排名时：经验、学历、语言和地点限制。
- 申请前：联系方式、简历版本、求职信偏好。
- 面试前：面试阶段和准备重点。

每次只提示当前动作真正需要的信息，并说明“跳过后会有什么影响”。

### 5.6 职位导入

页面只保留一个入口：

```text
粘贴职位链接 → 自动识别平台 → 尝试读取 → 失败时提示粘贴正文 → 保存并评分
```

对 BOSS/51job：

- 不要求用户填写 `--portal`、`--state-file` 或 `--archive-dir`。
- URL 和正文由界面传给 `tools/import_job.py`。
- 平台识别、原文归档、字段提取、去重和 `/rank` 路由自动完成。
- 遇到登录或 CAPTCHA 只提示用户处理，不自动重试或绕过。

## 6. 错误与状态设计

所有技术错误都转换为“状态 + 原因 + 下一步动作”：

| 内部状态 | 用户可见提示 | 下一步 |
|---|---|---|
| `AUTH_REQUIRED` | 猎聘尚未授权 | 点击“打开授权页”，完成后重新检查 |
| `AUTH_EXPIRED` | 猎聘授权已失效 | 重新授权，不自动重试登录 |
| `CLI_UNAVAILABLE` | 搜索工具未安装或不可用 | 点击“检查环境”，按提示安装 |
| `BLOCKED_PAGE` | 页面需要登录或验证 | 改用人工导入，不绕过验证 |
| `PARSE_DEGRADED` | 页面结构变化，暂时无法可靠读取 | 保留原文并切换人工导入 |
| `DETAIL_UNAVAILABLE` | 平台没有只读详情命令 | 使用职位链接读取或粘贴正文 |
| `BAD_INPUT` | 链接或文件格式不正确 | 显示具体字段和示例 |

错误页必须保留原始输入和可恢复操作，不让用户重新从头填写。

## 7. 成本控制与性能策略

### 7.1 使用成本

- 默认只运行用户选择的平台，不默认全量搜索。
- 搜索结果按 14 天窗口、每次约 20 条限制，延续现有 `/scrape` 规则。
- 使用本地去重和缓存，重复搜索不重复请求已见职位。
- 猎聘遵循官方 60 次/分钟共享配额，UI 不提供高频循环按钮。
- 健康检查和在线验证使用独立入口，不混入普通搜索。

### 7.2 技术成本

- P0 采用本地服务和静态页面，避免云端部署费用。
- 复用现有 CLI，不复制搜索、解析和评分逻辑。
- 简历解析优先使用本地已有工具；需要模型时明确显示可选的外部服务开关。
- 默认不上传原文、简历或职位数据；任何外部服务调用需单独确认。

## 8. 安全与隐私边界

- 敏感数据只写入现有受保护的本地文件，不写入日志、错误消息或 URL 参数。
- Token 继续由官方 CLI 的本地配置或环境变量管理，UI 不展示完整 Token。
- UI 编排层只允许调用已登记的只读搜索、详情、人工导入和排名动作。
- 投递、发消息、简历修改属于独立动作，必须保留人工确认；本方案不自动触发。
- 职位正文、简历文本和模型输出均视为不可信数据，不能改变工作流规则。
- 本地服务默认绑定 `127.0.0.1`，不暴露到局域网。

## 9. 分阶段落地计划

### P0：本地可视化 MVP（建议 3-5 个工作日）

1. 本地服务启动和健康检查。
2. 首页 5 个核心动作。
3. 首次设置向导和本地表单保存。
4. 一句话求职目标解析与确认。
5. 职位搜索任务编排，复用 `/scrape` 规则。
6. 搜索结果和排名结果只读展示。
7. BOSS/51job 人工导入页面，复用 `tools/import_job.py`。
8. 技术错误转用户动作提示。

### P1：输入简化与可靠性（建议 3-7 个工作日）

1. PDF/Word/纯文本简历提取。
2. 职位、技能和城市模板。
3. 渐进式资料补充和完整度检查。
4. 搜索条件自动保存与最近任务。
5. 平台健康状态页和诊断结果解释。
6. 导入/解析失败的原文恢复和重新处理。

### P2：分发和浏览器辅助（后续独立版本）

1. Windows 安装包和自动更新提示。
2. 浏览器扩展或当前页面一键导入。
3. 系统通知和任务历史。
4. 可选云同步（默认关闭，单独设计隐私和授权）。

## 11. 验收指标

### 11.1 使用门槛

- 不打开终端也能完成首次设置、搜索、导入和查看结果。
- 首次必填字段不超过 5 项。
- 新用户 5 分钟内可以启动一次搜索或导入一个职位。
- 用户不需要理解 JSON、CLI 参数、`seen_jobs.json` 或门户内部字段。

### 11.2 输入质量

- 上传简历后，用户无需重复录入大部分工作经历和技能。
- 一句话目标解析结果必须先确认，无法确定的字段不自动变成硬约束。
- 导入一个 BOSS/51job 职位不超过 30 秒（不含用户复制正文的时间）。
- 解析失败时原文 100% 可恢复。

### 11.3 安全与兼容

- Token、Cookie、密码、验证码和简历正文不出现在日志和 URL 中。
- 现有 CLI 和 Markdown workflow 可以独立运行。
- 现有门户字段、去重、排名和状态文件契约不被 UI 改写破坏。
- 任何投递、发消息或简历修改动作仍需要人工确认。

## 12. 发布与回滚策略

1. P0 先以本地开发启动器发布，不修改现有 CLI 默认入口。
2. 以只读搜索、查看和人工导入作为首批可用功能，申请动作继续沿用现有工作流。
3. UI 读写前先备份目标状态文件；失败时保留原文和上一版本状态。
4. 任何 UI 编排异常都可以退回 CLI，不能阻塞原有工作流。
5. 通过新手测试后再制作 Windows 安装包，不在未验证前默认开启云同步或自动授权。

## 13. 决策结论

推荐路线是：

```text
本地 Web 控制台
  → 一键启动
  → 一句话目标
  → 简历自动提取
  → 渐进式确认
  → 一键搜索/导入
  → 只读结果与清晰下一步
```

这条路线能够同时降低命令行操作成本和信息输入复杂度，同时最大限度复用已经完成的门户适配、标准化、去重、排名和人工导入代码。后续如果验证了用户需求，再将同一编排层打包为桌面应用或浏览器扩展。
